\begin{abstract}

Executable Archaeology is the practice of studying historical
computational systems by running their original code in a process
called ``reanimation''. Although AI-assisted programming is usually
considered a new invention, the idea of a program that helps write
programs is nearly as old as artificial intelligence itself. Here we
report on the reanimation of two historical AI programming assistants.
The first, Herbert Simon's Heuristic Compiler (1961), is an IPL-V
program that treats programming as a sort of problem-solving, 
applying means-end analysis to it. The second, KBEmacs (1984), was
the primary demonstration of MIT's Programmer's Apprentice project. It let
a programmer build up programs by combining standard ``clich\'es''
through a stylized English command language. Our reanimation of the
Heuristic Compiler reproduces the compiled code printed in Simon's
1963 paper, and our reanimation of KBEmacs exactly reproduces its December
1984 SQRT self-tests, although several remain to be completed. In the interest of emphasizing the obvious reflexivity,
we allowed most of the detailed reanimation reported here to be
carried out by a modern AI-assisted programming tool, Anthropic's
Claude Code, although it started from a significant base of existing
software, including a modern IPL-V interpreter, modern Common Lisp,
and an existing Common Lisp port of Spice Lisp Flavors, a reimplementation
of the Lisp Machine's object system.

\end{abstract}

\noindent\textbf{Keywords:} Executable Archaeology, History of AI,
Automatic Programming, Heuristic Compiler, KBEmacs, Programmer's
Apprentice).

\section{Introduction}
\label{sec:intro}

Modern programmers increasingly work alongside AI-based tools built on
large language models and trained on enormous corpora of source
code. Although the scale and fluency of the modern tools are truly novel,
the aspiration of a program that takes part in the work of programming is
nearly as old as programming itself. In the 1950s what we now call
compilation was referred to as ``automatic
programming''~\cite{backus1957fortran}. And within a few years of the
founding of artificial intelligence, researchers were asking whether
the methods of AI could be turned on the task of programming
itself~\cite{balzer1985,richwaters1988myths}.

This paper describes the ``reanimation'' of two historical systems
that represent two quite different approaches to AI-assisted
programming.\footnote{``Reanimation'' is the process of running
historical programs on emulation stacks, from code that is as close as
possible to the original~\cite{lane2025eliza}.} The first is Herbert
A.~Simon's \emph{Heuristic Compiler}, written in IPL-V in 1961 and
described in a RAND report that year~\cite{simonP2349} and in the
\textit{Journal of the ACM} in 1963~\cite{simon1963jacm}.  Simon asked
``whether the task of writing a computer program can be regarded as a
`problem' in the sense in which that term is used in GPS,'' the
General Problem Solver of Newell, Shaw, and
Simon~\cite{newell1959gps}. Given a description of what a routine
should do, Simon's tool searches for differences between where the
routine is and where the user wants it to be, and applies operators to
reduce this difference.

The second AI-assisted programming tool is \emph{KBEmacs}, the
Knowledge-Based Editor (in Emacs), built at MIT's Artificial
Intelligence Laboratory as the culminating demonstration of the
Programmer's Apprentice
project~\cite{waters1985tr,waters1986aimag,richwaters1987overview}.
The user of KBEmacs chose which standard algorithms (``clich\'es'') to
combine, and directed KBEmacs in stylized English. KBEmacs supplied
the details and wrote the code.

These two systems are separated by a quarter of a century, by
programming language (IPL-V on 1960s mainframes versus Zetalisp on MIT
Lisp Machines and their descendants), and by research tradition, yet
they stake out most of the conceptual territory that today's AI coding
tools occupy: How a programming task is specified, where the knowledge
needed to carry it out comes from, how work is divided between human
and machine, and how the system checks and explains what it has done.

We approached both as exercises in what has been called
\emph{executable archaeology}~\cite{shrager2026,moewsshrager2026}:
studying historical computational systems by reconstructing and
running their original code. The Heuristic Compiler was transcribed
from a 1961 line-printer listing in Simon's papers and run on the
Common Lisp IPL-V interpreter built earlier to run the Logic
Theorist. KBEmacs was transcribed from a four-volume January 1985
printout and run under a new Zetalisp compatibility layer for SBCL, a
modern Common Lisp. Both reanimations were themselves carried out
largely by an AI coding assistant: Anthropic's Claude~\cite{claude},
working in its command-line form, Claude Code. The division of labor
is described in ``Author Contributions and Use of AI''.

\section{Historical Background}
\label{sec:history}

\subsection{The Heuristic Compiler}

The phrase ``automatic programming'' has meant different things in
different decades, usually whatever was just beyond the current state
of the art. For the designers of FORTRAN it meant translating
algebraic formulas into machine code~\cite{backus1957fortran}. Such
translators are deterministic, and were neither then, nor are they
now, considered to be AI. Newell, Shaw, and Simon's work at RAND and
Carnegie Tech in the 1950s took a different view of what computers
could do. Their Logic Theorist (1956) searched for proofs of theorems
in \textit{Principia Mathematica}~\cite{LT1957,moewsshrager2026}, and
their General Problem Solver (1959) generalized these
methods into means-ends-analysis~\cite{newell1959gps}. Simon's 1963 summary of the method is
worth quoting in full, because the Heuristic Compiler implements it
almost literally:

\begin{quote}
Given the present and desired objects, find a difference between them.
Next, find an operator relevant to the difference; determine if the
operator can be applied to the present object. If so, apply it. (If
not, describe the objects to which it would apply and transform the
present object into an object of that kind---a new ``desired
object.'') Take the new object thus obtained as the present object and
repeat the process.~\cite[p.~494]{simon1963jacm}
\end{quote}

A proof and a program are not as different as it might seem; a proof
is a sequence of operators that transforms axioms into a theorem. In
other words, a proof is a program that generates a theorem as output
from the inputs that are axioms. In this sense (Simon continues), ``a
theorem-proving system can be regarded, at least formally, as a
program-writing system. Conversely, if we can formulate a programming
goal as a difference between a present and a desired object, we can
presumably use the same processes \ldots\ to generate a
program''~\cite[p.~495]{simon1963jacm}. The same observation, in a
deductive rather than heuristic setting, later became the foundation
of program synthesis from theorem
proving~\cite{green1969,mannawaldinger1971}.

Simon described the Heuristic Compiler in various publications and
reports in the early 1960s~\cite{simonP2349, simon1963jacm,
  simonRM3588}. He was explicit that his goal was \emph{not} to build an
automatic programming tool: ``no claims will be made for the heuristic
programming procedures described here as practical approaches to the
construction of compilers. Their interest lies in what they teach us
about the nature of the programming
task''~\cite[p.~493]{simon1963jacm}.

\subsection{The Programmer's Apprentice}

The Programmer's Apprentice (PA) project began at MIT in the
mid-1970s, with Charles Rich and Howard Shrobe's \textit{Initial
  Report on a LISP Programmer's
  Apprentice}~\cite{richshrobe1976}. These researchers were realistic
about the potential capabilities of such an AI-based programming tool
at that time: ``Recognizing that it will be a long time before it is
possible to fully duplicate an expert programmer's abilities, the
project seeks to develop an intelligent assistant system \ldots\ which
will help a programmer in various phases of the programming
task''~\cite[p.~47]{waters1986aimag}.

Over the following decade the project developed three central ideas:
\emph{Clich\'es} are standard computational methods, such as a linear
search, a report generator, or successive approximation, each with
\emph{roles} that vary from use to use and a fixed surrounding
structure. \emph{Plans} are a language-independent representation of
programs as hierarchical flowcharts with explicit data and control
flow, which Rich formalized in a Plan
Calculus~\cite{rich1981,richwaters1987overview}. And the \emph{assistant
approach} itself was a division of labor wherein the programmer makes
design decisions and the apprentice handles the routine details.
Waters's dissertation developed the analysis of programs into
plans~\cite{waters1978}.

KBEmacs was the realization of these ideas in a working editor. It ran
on MIT Lisp Machines, and their descendants, inside the Zmacs editor,
and handled both Lisp and Ada. Its best-known demonstration builds an
Ada report generator, \texttt{UNIT-REPAIR-REPORT}, from five commands
such as ``Define a simple-report procedure UNIT-REPAIR-REPORT'' and
``Fill the enumerator with a chain-enumeration of UNITS and
REPAIRS''~\cite[p.~48]{waters1986aimag},\cite{waters1985tse}.

KBEmacs was admittedly a research prototype. Waters wrote that it knew
``only a few dozen clich\'es'' where a practical tool ``would need to
know many hundreds,'' and that, its ideas having been used ``for
essentially all [they are] worth,'' KBEmacs ``has been
mothballed''~\cite[pp.~54--55]{waters1986aimag}. The project continued
with work on the Plan Calculus, on automated reasoning, and on
requirements and design apprentices, culminating in Rich and Waters's
1990 book~\cite{richwaters1990book}. 

\section{Reanimating the Heuristic Compiler}
\label{sec:hc}

\subsection{The Listing}

The source used here for the Heuristic Compiler is a line-printer
listing headed \texttt{HEURISTIC CODER 7/16/61}, discovered in the
Herbert A.~Simon Papers at the Carnegie Mellon University
Archives~\cite{simonlisting1961}. This listing is dated shortly
after RAND report P-2349, and is very nearly the program described in
that report. The listing is 94 line-printer pages, and about 4,470
lines of code (cards). We call this ``the deck''. The listing also
carries various hand markings indicating a handful of proposed
corrections. The deck contains an executive and two compilers; a
natural-language front end (a character scanner, dictionary, and
parser) intended to let the compiler accept English definitions; and a
small knowledge base about IPL-V, encoded as data, which the compilers
use to reason. The listing ends with the data and has no start card
(IPL-V type 5 card).

\subsection{Everything Is a Description List}

The central representational idea of the Heuristic
Compiler\footnote{Simon uses ``compiler'' at three levels, and a reader
meets all three within a page. The Heuristic Compiler as a whole is a
compiler; within it, two ``compilers,'' one for state descriptions and
one for functional descriptions, serve as the operators of its
means-end loop; and the code they build as list structures is finally
rendered as IPL-V text, a step closer to reverse compilation than to
compilation in the modern sense.} is that a
\emph{routine} is an object with attributes stored as an IPL-V
description list (approximately a lisp property list). Each attribute
is one possible definition of the routine: its IPL name, its
\emph{functional description} (i.e., a process name plus arguments,
such as ``INSERT ( ) AT END OF ( )''), its \emph{state description}
(i.e., which cells it affects, and what each holds before and after),
its flow diagram, and its IPL-V code. Within the IPL code rendered in
this representation, IPL-V instructions are themselves description
lists with attributes for each field. And a symbol such as \texttt{J3}
is a description list with a region (the letter J) and a location (the
integer 3). The program never handles IPL code as text; it builds the
textual form of the generated code via a ``compiler'' that processes
these structures, only printing out the textual form at the end.

The Heuristic Compiler's executive implements a means-end
problem-solving loop whose \emph{differences} are kinds of definitions
and whose \emph{operators} are whole compilers (described just
below). The executive finds the closest definition for the routine,
looks up the relevant compiler in a table of connections, applies it,
and tests whether the routine has improved. If the routine has not
improved, the executive gives up.

The \emph{state description compiler} is the most GPS-like part of
the Heuristic Compiler. It compares the input and output states of
each affected cell, classifies the largest difference (addition,
deletion, replacement, or copying), looks up an operator relevant to
it, binds the operator's variables to the actual cells, and then
recursively compiles two subproblems: getting from the original input
state to the required state, and getting from the operator's output
state to the desired output. Its knowledge of IPL-V consists of
exactly two operators, LOAD and REPLACE, each itself a tiny routine
with its own state description.

The \emph{functional description compiler} works by analogy. Given a
routine described as, say, ``INSERT (1) AT END OF THE VALUE OF THE
ATTRIBUTE (0) OF (2),'' it searches the routines already compiled for
one with the same \emph{process}, here ``INSERT (0) AT END OF (1),''
whose code is the single primitive \texttt{J65}. It then adapts that
routine to the new arguments, moving the inputs into working cells,
compiling code to fetch each argument, recursing when an argument is
itself a described computation (a ``determiner''), and wrapping the
result in instructions that save and restore the working cells.

\subsection{Running The Heuristic Compiler}

The deck runs on the Common Lisp IPL-V interpreter originally written
to run the Logic Theorist~\cite{shrager2026,shragerrepo}. Claude
extended the interpreter with several primitives (J-functions) needed
by the Heuristic Compiler that were not required by the Logic
Theorist. It also added a start card. With these changes, the program
runs and reproduces Simon's published examples.

\textbf{Compiling from a functional description.} Given the functional
description of INSERT AT END OF VALUE LIST, the program produces
\texttt{J13 J52 11W2 11W0 J10 11W1 J65 J32 0}, character for character
the code in the 1963 paper~\cite[pp.~499--500]{simon1963jacm}
(Figure~\ref{fig:insert}). A print left in routine U113 shows the code
growing one argument at a time, which reproduces the sequence of
stages through which the paper walks its readers. In Simon's runs, as
in ours, the functional description is supplied as a hand-coded list
structure, not as typed English; the phrase is printed from it, but
the compiler matches processes by symbol identity. The English front
end in the deck has not yet been run (see ``Next Steps'').

\textbf{Compiling from a state description.} Simon's running example
of the state description compiler is J3, SET SIGNAL MINUS: a routine
that replaces the top symbol of the signal cell H5 with the symbol J3
(``minus''). The state description says that H5 goes from \emph{some
symbol on top of the rest of its pushdown list} to \emph{J3 on top of
the same rest}. The compiler finds a replacement difference in a named
cell; finds REPLACE relevant, with its variable bound to H5, giving
\texttt{20H5}; sets up the prefix subproblem ``get J3 into the
communication cell,'' an addition, for which LOAD is relevant, giving
\texttt{10J3}; finds no suffix subproblem; and assembles \texttt{10J3
  20H5 0}, the code in the paper~\cite[p.~498]{simon1963jacm}.

There is a catch, and it is the kind of thing only running the program
reveals. \emph{As listed, the deck does not compile J3.} The listing's
J3 has both a functional and a state description, and the executive
always prefers the functional description, on the stated assumption
that ``it is easier to compile from a functional description than from
a state description''~\cite[p.~502]{simon1963jacm}. No
already-compiled routine shares J3's process, the functional
description compiler fails, the executive sees no progress, and it
gives up without ever trying the state description. The paper's J3
result is obtained only when J3's functional description is removed
before the run, after which the state description compiler produces
exactly the published code. The 1963 listing in RM-3588-PR suggests
what happened: its executive is card for card the same, but the cards
that give J3 a functional description are numbered as later
insertions. Most likely the paper's J3 came from a version in which J3
had only a state description.

\textbf{Flow diagrams.} The paper's last section handles routines with
branches and loops by decomposing them into \emph{segments} joined by a
flow diagram. The program reassembles routine J77 (``test whether there
is a symbol equal to 0ACCUMULATOR on list 1ACCUMULATOR'') from its
segments, and decomposes it again into the paper's flow diagram.

\textbf{The information annexer.} RM-3588-PR's Appendix~B, a small
program that stores statements such as ``X114 is the X33 of the X25 of
X105'' into description lists, either identifying an object already in
memory or creating one, was also transcribed and runs. Its
output matches the fragment of 1963 output that survives in the
memorandum~\cite{simonRM3588,earepo}.

\subsection{Implementation Notes}

One print routine, U126, is called but absent from the 1961 listing;
it was supplied from the 1963 listing in RM-3588-PR,
Appendix~A~\cite{simonRM3588}, and affects only printing. A start card
for the demonstration routine T1 was added (the 1963 listing ends with
exactly such a card). The 1963 state description compiler differs from
the 1961 one in representing states by bare symbols where the 1961
version holds described ones. The information annexer of RM-3588-PR,
Appendix~B, is 409 cards.

\section{Reanimating KBEmacs}
\label{sec:kbe}

\subsection{The Listings}

The surviving KBEmacs source is a January 1985 printout, four bound
volumes of Zetalisp listings, preserved by Kent~Pitman, a member of
the KBEmacs team, whose scans are at
\url{https://github.com/netsettler/netsettlement/tree/main/kbe}~\cite{pitmanscans}. These
cover the system as of KBE version 358.0x (December 1984), although
individual files carry their own dates and versions. Volume~1 opens
with something unusual and extremely useful to an archaeologist: the
results of KBEmacs's automatic self-test, run ``Friday the fourteenth
of December, 1984; 2:25:23 pm'' on the Lisp Machine \emph{Merlin}. The
self-test runs six command sequences, compares the code KBEmacs
generates with expected code, and reports that three sequences (HASH,
SQRT, and SUMLIST) succeeded and three (BUCKET, DELETE, and MEMQ)
failed with ``Bad code generated.''

The 87 files were transcribed (mostly by ChatGPT~\cite{chatgpt}) into
about 34,500 lines of source, now at
\url{https://github.com/jeffshrager/kbemacs}~\cite{kbemacsrepo},
roughly consistent with Waters's description of the system as ``some
40,000 lines of Lisp code''~\cite[p.~55]{waters1986aimag}.

\subsection{Text and Plans}

A KBEmacs user works in a stylized English command language phrased in
terms of clich\'es and their roles. The clich\'e library is written as
code with holes, as in the definition of successive approximation
in Figure~\ref{fig:cliche}.

\begin{figure}[H]
\begin{lstlisting}
(DEFINE-CLICHE SUCCESSIVE-APPROXIMATION

    COMMENT "iteratively improves an approximation until {the criterion} is
             satisfied" ...)
  (LET* ((APPROXIMATION {the input initial-approximation}) )
    (LOOP DO
      (IF ({the criterion} APPROXIMATION) (RETURN APPROXIMATION) )
      (SETQ APPROXIMATION ({the improvement-step} APPROXIMATION) ))))
\end{lstlisting}
\caption{A clich\'e from KBEmacs's library (\texttt{kbelib.lisp}, 1984).
The braces are KBEmacs read syntax marking \emph{roles}, the parts that
vary from use to use; the surrounding code is fixed.}
\label{fig:cliche}
\end{figure}
Clich\'es are not stored as text. When the library loads, each
definition is run through KBEmacs's \emph{analyzer}, which turns code
into a plan: a set of facts in a small database describing segments,
ports, data flow, control flow, and roles. In a plan, a \texttt{LOOP}
with a \texttt{SETQ} disappears; what remains is a temporal
composition of a sequence of states. The knowledge-based editor
operates on plans, and after every command the \emph{coder} turns the
plan back into program text, deciding where to nest expressions and
where to introduce variables, and preferring names the programmer has
already used. Waters called this two-way translation the
\emph{representation shift}, and argued that it gave plans locality,
additivity, and modularity that text lacks~\cite{waters1986aimag}.
Because the user may also simply edit the text, KBEmacs must keep text
and plan consistent in both directions.

\subsection{Running KBEmacs (headless)}

KBEmacs depends heavily on the Lisp Machine environment of its time,
including Flavors (the Lisp Machine's object system), the Zmacs editor,
Lisp Machine processes, Waters's own LetS loop notation, and Zetalisp
itself, which is similar to, but not exactly the same as, modern Common
Lisp. Emulators survive for the MIT CADR Lisp Machine (usim) and for
Symbolics Open Genera, but no usable environment compatible with this
KBEmacs release (Symbolics Release 4.5) was available to us. Both
include Flavors, but Open Genera, the closer of the two, is not freely
available, and it corresponds to a Genera release about a decade later
than the one KBEmacs ran on. The reanimation targeted the
\emph{headless} core (the database, analyzer, clich\'e library,
command language, knowledge-based editor, and coder), leaving out the
editor, windows, actors, and the Ada front end~\cite{kbemacsrepo}.

The 1985 source, with correction of minor typos and transcription
errors, is loaded into SBCL (\url{https://www.sbcl.org}), a modern
Common Lisp, through a Zetalisp compatibility layer that Claude
assembled and debugged. The largest
single piece of that layer is g000001's Common Lisp port of Spice Lisp
Flavors, CMU's reimplementation of the Lisp Machine's Flavors
object-oriented programming system~\cite{g000001}.\footnote{Coincidentally, Spice Lisp (which
was built at CMU, where Simon and Newell taught) became CMUCL, and
SBCL is a fork of CMUCL.}

The rest of the layer supplies the parts of Zetalisp and the Lisp
Machine that Common Lisp lacks or does differently. A small driver was
also added to replay a self-test sequence from the 1984 record and
compare the generated code with the expected code, as did the original
test harness.

The SQRT sequence (Figure~\ref{fig:sqrt}) builds a square-root routine
from three clich\'es in seven commands, and then builds a variant with
an extra parameter in seven more. After the first command that names a
clich\'e, KBEmacs holds the clich\'e's structure with its roles still
open as holes; each further command fills a role with code or with
another clich\'e, whose own unfilled roles appear as new holes. After
seven commands the plan has 32 segments and the program is complete.

\begin{figure}[H]
\begin{lstlisting}
>Reinitialize database.
>Define a program MYSQRT with a parameter NUM.
>Implement it as a successive-approximation.
>Implement the initial-approximation as [1.] .
>Implement the improvement-step as an average of [APPROXIMATION]
   and [(// NUM APPROXIMATION)] .
>Implement the criterion as an equality-within-epsilon of
   [(* APPROXIMATION APPROXIMATION)] and [NUM] .
>Implement the epsilon as [0.0001] .

(DEFUN MYSQRT (NUM)
  (LET* ((APPROXIMATION 1))
    (LOOP DO
      (IF (< (ABS (- (* APPROXIMATION APPROXIMATION) NUM)) 0.0001)
          (RETURN APPROXIMATION))
      (SETQ APPROXIMATION (// (+ APPROXIMATION (// NUM APPROXIMATION)) 2.0)))))

The program MYSQRT is a successive-approximation. The initial-approximation is 1.
The criterion is an equality-within-epsilon ...
\end{lstlisting}

All fourteen commands run, and both generated programs are
\texttt{equal} to the code recorded in 1984. The generated code also
works: \texttt{(mysqrt 2.0)} returns 1.4142157.

\subsection{Implementation Notes}

The reanimation loads the \emph{headless} core of KBEmacs (database,
analyzer, clich\'e library, command language, knowledge-based editor,
and coder) in the order given by its own system definition, under SBCL.
The Zetalisp compatibility layer consists of g000001's Common Lisp
port of Spice Lisp Flavors~\cite{g000001}, with a few bug fixes,
extended with the Lisp Machine's \texttt{:case} method combination
(with \texttt{:otherwise}), \texttt{send} to functions and streams, and
flavor-aware \texttt{typep}; g000001's port of Waters's LetS series
notation~\cite{g000001}; and definitions of the Zetalisp special forms
and functions that differ from Common Lisp.

\section{Then and Now: Historical Approaches to AI-Assisted Coding}
\label{sec:thenandnow}

Neither the Heuristic Compiler nor KBEmacs is an ancestor of today's AI
coding assistants in any direct technical sense. Large language models
are trained, not programmed with explicit operators or clich\'es, and
they operate on program text rather than on description lists or plans.
Nonetheless the questions these two systems were built to
explore are recognizably the questions that shape AI-assisted
programming today. The comparisons that follow are conceptual
continuities, not architectural equivalences.

\textbf{How is a programming task specified?} Simon's two compilers
differ precisely in how the task is described. A state description
says what the machine looks like before and after, which is close to
what we would now call a specification by examples or by
pre- and post-conditions, and close to the role unit tests play in
directing a modern assistant. A functional description is an imperative
phrase, which is close to a natural-language prompt. Simon drew a
conclusion that remains apt: programmers use both, but ``at the higher
levels \ldots\ a language of functions appears generally the more
natural and powerful,'' and ``the mappings from functional descriptions
to process language are simpler and more direct than the mappings from
state descriptions''~\cite[p.~506]{simon1963jacm}. KBEmacs chose the
functional side and gave it a vocabulary of named algorithms. Today's
assistants accept both kinds of description, and much of the craft of
using them lies in combining a functional request with a test-like
check.

\textbf{Where does the knowledge come from?} Both historical systems
are knowledge-starved by modern standards. The Heuristic Compiler's
state description compiler knows exactly two operators; its functional
description compiler can compile a routine only if a routine with the
same process has already been compiled. KBEmacs knew ``a few dozen''
clich\'es; Waters estimated that a practical tool would need ``many
hundreds''~\cite[p.~55]{waters1986aimag}. Both systems identified
reuse of known solutions as the heart of the matter: Simon's
functional compiler works by finding an analogous routine and adapting
it, and the whole Programmer's Apprentice rests on the claim that
programs are built from background knowledge. What neither could solve
was acquiring that knowledge at scale. Large language models can be
loosely described as one answer to precisely this bottleneck: in
effect, an implicit clich\'e library absorbed from an enormous body of
code. This is a metaphor, not a claim about what such models actually
represent, and it comes at the price of having no explicit, inspectable
representation of what a clich\'e is or what its roles are. 

\textbf{Who does what?} The Heuristic Compiler was meant to be
autonomous; KBEmacs was deliberately an apprentice, leaving design
decisions to the programmer and taking over ``the details.'' Waters's
argument for the apprentice was practical: full automation was not
near, and a semiexpert assistant could be useful at once. Modern tools
have traversed the same axis in a few years, from completing a line,
to writing a function on request, to agents that plan, edit, and test
across a code base with varying degrees of
supervision~\cite{yang2024sweagent,jimenez2024swebench}. The question
of where the programmer's decisions end and the machine's begin,
central to the Programmer's Apprentice, is again a live design
question.

\textbf{How does the system know it is making progress?} The Heuristic
Compiler's executive is a loop: apply a compiler, test whether the
routine has moved to a better kind of definition, and stop if it has
not. Its state description compiler implements difference reduction in
the strict GPS sense. Modern coding agents commonly run a loop of a
similar shape~\cite{yang2024sweagent}: make a change, run the tests or the compiler, examine
the difference between what happened and what was wanted, and try
again. The difference detector is now an executed test suite rather
than a hand-coded comparison of states, and the operator is a learned
model rather than a table of connections, but the architecture of
means-end iteration is recognizable. The resemblance goes beyond the
loop. A coding agent of this kind is not a purely neural system: the
language model chooses what to do next and interprets the results, but
the processes of compiling, executing, comparing outputs, tracking
changes, and so on, are done by conventional symbolic programs. In the
work reported here these were a Common Lisp compiler, an IPL-V
interpreter, and the 1984 self-test's own comparison of generated with
expected code. Although the heuristics have moved from a hand-written
table of connections into a learned model, the operators and the
difference tests are still ordinary programs. KBEmacs, for its part,
came with a self-test in which the expected output was code, which is
exactly what made it possible to check its reanimation.

\textbf{Representation and explanation.} The two historical systems
never treated code merely as text. The Heuristic Compiler builds IPL
instructions out of description lists and prints them only at the end;
KBEmacs reasons about plans and regenerates code after every command,
taking pains to keep code and plan consistent when the user edits the
code directly. That explicit representation is what allowed KBEmacs to
describe a program in terms of its design (``The program MYSQRT is a
successive-approximation \ldots''). Today's assistants operate on text
and also explain code fluently, but their explanations are generated
from text, not read off an explicit representation of the design. The
trade-off between the robustness of working with text, which KBEmacs
found painfully expensive to analyze---Waters reports that ``well
over half of all the effort expended on KBEmacs went into implementing
an analyzer and coder''~\cite[p.~55]{waters1986aimag}---and the
inspectability of working with plans, has not gone away.

\section{Next Steps}
\label{sec:next}

For the Heuristic Compiler, the largest piece of unexplored territory
is the English front end: the scanner, dictionary, and parser, and the
routine that converts a parse into a functional description. Simon
credited H.~S.~Kelly with ``linguistic components for the compiler
which are omitted from this report''~\cite[p.~506]{simon1963jacm};
these routines may be them. Running them requires input sentences,
which are not in the listing. 

For KBEmacs, the compatibility layer was debugged against the one
self-test sequence whose expected output was known, so a skeptic may
reasonably ask whether it is tuned to SQRT. The next step is therefore
to run the other five sequences of the 1984 self-test without changing
the layer after seeing their results, aiming to reproduce both the
three successes and the three failures, and to build a new KBEmacs
program that is not among the self-tests. After that comes the Ada
front end, which would allow Waters's
\texttt{UNIT-REPAIR-REPORT} demonstration to be reproduced.

reproduced their historical output. Claude also drafted this
